# x402 pay-per-call mode

Scout can read Zerion analytics without an API key. A dedicated payment wallet pays each accepted data request through x402. It is separate from the wallet Scout observes.

Zerion lists API keys, x402, and MPP as authentication choices in its [authentication guide](https://developers.zerion.io/authentication). Its [CLI guide](https://developers.zerion.io/build-with-ai/zerion-cli) limits x402 pay-per-call access to analytics. Scout follows that boundary. It uses an EVM payment wallet on Base and has no trading command.

## Payment flow

1. Scout sends the analytics request without an API key.
2. Zerion returns payment requirements with HTTP 402.
3. The x402 SDK parses the selected requirements and calls Scout's pre-signing
   guard immediately before payment creation.
4. Scout validates Base mainnet, the exact Base USDC contract, the pinned
   recipient, a bounded timeout, and the configured cap. Only then does it reserve
   budget and allow payment creation.
5. The SDK signs the payload and retries the request with `PAYMENT-SIGNATURE`.

Scout is intentionally Base-only in this adapter. A non-Base requirement is
rejected before signing. This keeps chain selection explicit and avoids
assuming that a payment shape accepted on one rail is valid on another. If
Solana support is added later, it needs a separate asset and facilitator
policy; [Coinbase CDP SDK issue #795](https://github.com/coinbase/cdp-sdk/issues/795)
is a public example of a reported hosted exact-SVM compute-limit rejection,
not evidence that Scout's Base route or every facilitator is broken.

## Setup

x402 runs only from an MCP server entry you write yourself. The Claude Code plugin sets `SCOUT_ENABLE_X402` to an empty value in its own server entry. That empty value overrides an `export SCOUT_ENABLE_X402=1` in the shell that launches Claude Code (verified on Claude Code 2.1.273), so the plugin stays off x402. Other MCP entries and other hosts do inherit an exported value, so set `SCOUT_ENABLE_X402=1` only on the one server entry that should pay, never in your shell profile. A host entry for Cursor or any stdio client looks like this (Codex uses the same variables under `[mcp_servers.scout-portfolio]` `env`):

```json
{
  "mcpServers": {
    "scout-portfolio-x402": {
      "command": "uvx",
      "args": [
        "--from",
        "scout-portfolio-manager[x402] @ git+https://github.com/gabchess/scout-onchain@v0.7.1",
        "scout-portfolio-manager"
      ],
      "env": {
        "SCOUT_ENABLE_X402": "1",
        "ZERION_WALLET_ADDRESS": "0xObservedWallet",
        "ZERION_X402_PAY_TO": "0xExpectedRecipient"
      }
    }
  }
}
```

Keep `ZERION_X402_PRIVATE_KEY` out of that file. Supply it through your host's secret manager or the environment that launches the host.

From a source checkout, install the payment and MCP extras:

```bash
uv sync --extra x402 --extra mcp
```

Load the payment key through your host's secret manager. For an interactive shell, read it without echo and pass every x402 variable inline to the one command, so nothing is exported to later processes:

```bash
read -s ZERION_X402_PRIVATE_KEY
ZERION_X402_PRIVATE_KEY="$ZERION_X402_PRIVATE_KEY" \
  ZERION_WALLET_ADDRESS=0xObservedWallet \
  ZERION_X402_PAY_TO=0xExpectedRecipient \
  SCOUT_ENABLE_X402=1 \
  uv run --extra x402 --extra mcp zpm-mcp
```

| Variable | Meaning |
|:--|:--|
| `SCOUT_ENABLE_X402` | Required; must be exactly `1`. Without it Scout ignores the x402 key |
| `ZERION_X402_PRIVATE_KEY` | Private key for the dedicated Base payment wallet |
| `ZERION_WALLET_ADDRESS` | Address whose portfolio Scout reads |
| `ZERION_X402_MAX_USD_PER_CALL` | Cap for one payment payload; default `$0.05` |
| `ZERION_X402_MAX_USD_PER_SESSION` | Process-lifetime budget; default is the per-payment cap multiplied by 21 |
| `ZERION_X402_PAY_TO` | Required; the only address Scout will pay |
| `ZERION_CHAIN` | Snapshot label only; reads are not filtered by chain; default `multi-chain` |

API-key and x402 modes are exclusive. Partial or conflicting configuration stops startup.

`SCOUT_ENABLE_X402=1` is new in 0.7.0 and breaks older x402 setups until you add it to your MCP server entry. Claude Code passes the launching shell's environment to plugin MCP servers, so an exported payment key reaches the plugin process. The Claude Code plugin sets `SCOUT_ENABLE_X402` to an empty value in its own server entry. That empty value overrides an `export SCOUT_ENABLE_X402=1` in the shell that launches Claude Code (verified on Claude Code 2.1.273), so the plugin stays off x402. Other MCP entries and other hosts do inherit an exported value, so set `SCOUT_ENABLE_X402=1` only on the one server entry that should pay, never in your shell profile.

## Cost boundary

A nominal maximum-page snapshot can request one positions page and 20 transaction pages. With the default `$0.05` payment cap, the default process budget is `$1.05`.

Scout installs its budget check immediately before the SDK creates every payment payload. It reserves the full per-payment cap. Recovery payloads use the same budget. If another reservation would exceed the session maximum, Scout stops before signing and returns a non-retryable `budget` error.

The pre-signing guard also rejects malformed or over-cap atomic amounts, a
missing recipient, a missing or over-long timeout, and any asset other than the
pinned Base USDC contract. After the SDK's paid retry, Scout requires a non-empty
`PAYMENT-SIGNATURE` header on the retry request. A missing header is a
non-retryable `payment` error.

### Pin the recipient

The amount, asset and **recipient** all arrive in the server's 402 response, so
the recipient is untrusted input that decides where money goes.

`ZERION_X402_PAY_TO` is required. Set it to the address you expect and Scout
refuses any other with a `pay_to_not_allowed` error, comparing case-insensitively.
Leave it out and x402 refuses to start: a missing pin used to mean "pay whoever
the server names", which made an attacker-chosen recipient correct behavior.

The check is enforced twice on purpose. Startup decides whether the operator
configured a recipient at all; the guard decides whether the server named the
right one. Only startup can tell those apart, and a missing pin surfacing
mid-run as a 402 would read like an endpoint fault.

The timeout has no switch, because there is no reason to raise it. The server's
requested `max_timeout_seconds` becomes the EIP-3009 `valid_before` or the
Permit2 `deadline`, so an unbounded value leaves a redeemable authorization
outstanding for as long as the server likes. Scout caps it at 600 seconds and
rejects anything larger with `timeout_too_long`.

This accounting is conservative. A reservation remains spent in Scout's ledger after a payment error because settlement may be ambiguous. A process restart creates a new budget. Set `ZERION_X402_MAX_USD_PER_SESSION` explicitly when the host needs a different limit.

The watch report performs one shared wallet snapshot, then derives PnL, analysis, DCA windows, and alert results in memory. It displays the remaining x402 budget.

## DCA boundary

x402 pays for analytics. It cannot authorize a trade in Scout.

With an API key, Scout still ends DCA work at an approval-required proposal. A host may supply quote fields to `preview_dca`. The optional Zerion CLI preparation path can obtain unsigned proposals. Scout cannot sign an order or submit a transaction.

## Failure handling

An HTTP 402 response or SDK payment failure becomes a non-retryable `payment` error. A budget stop becomes a non-retryable `budget` error. Inspect the payment wallet and provider response before another attempt.

Transport, rate-limit, and provider errors retain their own typed responses. The live source never falls back to the fixture.

The automated suite builds the real SDK session and tests the budget hook without sending funds. This repository has no verified paid live x402 request.

## Solana failure fixture

[`fixtures/x402/solana_compute_limit_regression.json`](../fixtures/x402/solana_compute_limit_regression.json)
is an offline test vector modeled on [Coinbase CDP SDK issue #795](https://github.com/coinbase/cdp-sdk/issues/795).
The report describes exact-SVM payments that reportedly succeeded around 20,000
compute units and were rejected around 100,000. The fixture labels this as
reported evidence, not an independent reproduction or a claim that a hosted
facilitator is currently broken. Scout uses it to prove that a Solana request
is rejected before budget reservation, signing or facilitator retry.
