# x402 pay-per-call mode

Scout can read Zerion without an API key. A dedicated payment wallet authorizes each API fee through [x402](https://docs.x402.org/).

## Payment flow

1. Scout sends a request without an API credential.
2. Zerion returns HTTP 402 with payment requirements.
3. The x402 SDK signs a USDC authorization and resends the request.
4. Zerion returns the same data shape used by API-key mode.

[Zerion documents](https://developers.zerion.io/build-with-ai/x402) USDC payment on Base or Solana. Scout 0.4.0 configures the EVM path on Base. The payment wallet needs USDC on Base. Provider price and settlement terms can change.

## Setup

```bash
uv sync --extra x402 --extra mcp
export ZERION_X402_PRIVATE_KEY=$(cat ~/secrets/x402-payment-key)
export ZERION_WALLET_ADDRESS=0xObservedWallet
uv run --extra x402 --extra mcp zpm-mcp
```

| Variable | Meaning |
|:--|:--|
| `ZERION_X402_PRIVATE_KEY` | Private key for a dedicated Base payment wallet |
| `ZERION_WALLET_ADDRESS` | Address whose portfolio Scout reads |
| `ZERION_X402_MAX_USD_PER_CALL` | Per-payment cap; default `$0.05` |
| `ZERION_CHAIN` | Snapshot label; default `multi-chain` |

API-key and x402 modes are exclusive. Partial or conflicting configuration stops the server.

## Cost and signing boundary

The observed wallet supplies an address only. The x402 wallet holds signing authority inside the SDK session and pays data fees. Use a dedicated wallet with a small balance.

The SDK enforces `ZERION_X402_MAX_USD_PER_CALL` for each payment. Scout 0.4.0 has no cumulative spend budget. A snapshot makes one positions request and up to 20 transaction-page requests. That means up to 21 top-level API requests with the default page limit.

One top-level request includes the initial 402 exchange and paid resend. The SDK can make one further paid recovery attempt. A per-payment cap does not bound total session spend.

Scout keeps the private key out of its returned errors, logs, object representations, and tool results. The host environment and third-party SDK remain separate trust boundaries.

## Failure handling

An HTTP 402 response or SDK `PaymentError` becomes error kind `payment` with `retryable: false`. A signed request may have reached the facilitator before the failure became visible. Inspect the payment wallet and provider response before another attempt.

Connection failures that occur outside the payment flow remain `transport` errors. The live source has no fixture fallback.

The automated suite builds the real SDK session and tests error handling offline. This repository has no verified live paid x402 request.
